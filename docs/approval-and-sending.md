# 승인과 전송

AI가 만든 문장이 방송에 나가려면 **사람이 고른다.** 자동 전송 경로는 없다.

## 후보 카드

Discord 채널에 카드 하나를 유지한다(올리기 전에 이전 카드를 지운다). 카드에는:

- 상태: 시각, 다음 판단 조건, 최근 전사, 채팅 분위기
- 판단 결과: "✅ 후보 올림" / "🤐 안 올림 + 이유" / "💤 최근 채팅 없음" / "⏸️ 생성 OFF"
- 후보 버튼: 문장이 버튼 라벨이다. 누르면 **그 문장이 바로 방송으로 나간다**(카드 하나에서 하나만)

판정 경로는 셋이다.

| 경로 | 입력 | 쓰임 |
| --- | --- | --- |
| 버튼 | 카드의 문장 버튼 | 기본. 후보 문장 중 하나 선택 |
| 리액션 | 후보 메시지에 ✅/❌ | 운영자 계정이 단 것만 인정 |
| 답장 | `ㅇㅇ`, `거부`, `ㅇㅇ 짧게` | 승인/거부/첨언 |

세 경로 모두 `store.set_verdict()` 하나로 모인다. 판정은 `candidates.jsonl`에 반영하고
`training.jsonl`에 한 번만 append한다(중복 방지).

## 저장소 동시성

생성·콘솔·게이트웨이·리액션 감시가 같은 파일을 만진다.

- `candidates.jsonl`은 읽기-수정-전체쓰기(`.tmp` → `os.replace`)를 `flock` 안에서 한다.
- append는 별도 락으로 잠근다.
- `training.jsonl`은 `message_id` 기준 중복 append를 막는다.
- 판정에는 `decided_at`, `live_sent`, `send_ms`(전송 소요), 호출자(`파일:줄:함수`)를 남긴다.

## 실제 전송

`ws_send.send_message(text)`:

1. 전송 가드
   - 같은 문장 10분 내 재전송 금지(`sent.jsonl`)
   - 최소 간격 3초(연타 방지). 시간당 상한은 두지 않았다 — 매 건 사람이 고르므로 의미가 없다
2. 방송 정보 + 로그인 쿠키로 `CHATNO`·`FTK`·계정 상태 확인
3. WebSocket 로그인 → JOIN → ENTER_INFO → `CMD 5` 전송
4. 성공 판정: 응답 `ret in (0, 5)` **그리고** 에코 본문이 보낸 문장과 일치

성공 판정을 `ret`만으로 하면 실패를 성공으로 읽는다. 응답 코드가 두 형태로 오기 때문이다.

전송에 실패해도 판정은 승인으로 남는다. `live_sent=false`로 기록되므로 나중에 구분할 수 있다.

## 승인 데이터의 함정 ("복사 보상")

초기 감사에서 드러난 문제:

- 후보 196건 중 판정된 것은 12건(6%).
- 승인 6건 **전부** 내 과거 발화와 글자 단위로 일치했다.
- 프롬프트에 고정 예시 10개가 박혀 있었으므로, 생성기는 "예시를 그대로 쓰면 승인된다"를 학습할 수 있었다.

즉 그 데이터는 **선호 신호가 아니라 복사 보상**이었다. 조치:

1. 고정 예시를 프롬프트에서 빼고 "금지 목록"으로만 쓴다.
2. 승인/거부 예시를 넣을 때 시드 코퍼스와 글자 일치하는 것은 제외한다(홀드아웃).
3. 승인 데이터가 1,000건을 넘기 전에는 분류기·파인튜닝에 쓰지 않는다.

## 판정 통계 (2026-11-02 시점 로컬 기록)

| 항목 | 값 |
| --- | --- |
| 수집 채팅 | 1,661줄 / 서로 다른 닉 21 |
| 생성 후보 | 246 |
| 판정 | 118 (승인 9 / 거부 109) |
| 실제 방송 전송 확인 | 1 |

승인률 8%는 "취향이 까다롭다"기보다 **후보 품질이 낮았다**는 뜻으로 읽는 게 맞다.
거부 기록에는 사유 필드가 없어서(당시 저장 포맷) 사유별 집계는 없다. 다만 거부된 문장의 평균 길이는
10.6자로, 승인된 짧은 반응보다 길었다. 같은 기간 수동 점검에서 확인된 유형은 남의 말 되받기·설명조·
흐름과 무관한 새 주제였다(정성 관찰, 집계 아님).
